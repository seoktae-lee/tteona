chmod 400 ~/Downloads/에어론\ 펨키/aeron-web-key.pem chmod 400 ~/Downloads/에어론\ 펨키/aeron-was-key.pem chmod 400 ~/Downloads/에어론\ 펨키/aeron-db-key.pem

서버 사이드 Vlog 생성 (FFmpeg)

⏱ 2~3주 WAS 서버 🔥 핵심 차별화
🎬 비유: 편집실 외주 → 자체 편집실 운영
지금은 사용자 폰(편집실 없는 일반인)이 직접 영상을 합치느라 버벅거립니다. 이 단계에서는 WAS 서버(8코어 전문 편집실)에서 처리합니다. 사용자는 클립만 보내면 완성 영상을 받을 수 있고, BGM·자막·트랜지션·멀티 포맷까지 추가됩니다.
서버 파이프라인 구축
클립 업로드 API 엔드포인트 구현 (완료·배포)
POST /api/vlog/jobs(잡 생성) → POST /jobs/:id/clips?order=N(multipart, 디스크 저장, 개당 300MB) → POST /jobs/:id/start(큐 투입) → GET /jobs/:id(진행률 폴링). nginx /api/vlog/ 전용 한도 300M + 업로드 스트리밍.
DB에 Vlog 작업 큐 테이블 구현 (완료)
Phase 2의 vlog_jobs 테이블 활용. enum에 'uploading' 추가(uploading→pending→processing→completed/failed). 워커가 5초마다 pending 1개 처리(동시 1개 — 8코어 집중), progress 실시간 갱신.
FFmpeg 합성 로직 구현 (완료·E2E 검증)
로컬 AVFoundation과 동일 스타일: 타이틀 카드 2초(주황 #FFB587 + 한글 날짜 + tteona, Gowun Batang 폰트 서버 업로드) + 클립별 정규화(첫 클립 방향 기준 1080p, scale+pad, 회전 메타 처리) + 장소명 자막(반투명 박스) + 페이드 0.4초 + 동일 인코딩 세그먼트 concat(-c copy, faststart). 3클립 E2E: 업로드→합성 10초→1080x1920 h264/aac 11.1초 결과물, 타이틀·한글자막 프레임 검증 통과.
추가 기능
BGM 자동 삽입 (완료·E2E 검증)
저작권 프리 12곡을 태그별 3곡씩 서버 배치(assets/bgm/{couple,friends,family,solo}). 태그 폴더에서 랜덤 선택, 원음 유지 + BGM 30% 볼륨 amix(normalize=0), 영상 길이에 맞게 루프·컷 + 끝 1.5초 페이드아웃. 영상 스트림은 재인코딩 없음(-c copy)이라 빠름.
멀티 포맷 출력 (릴스 9:16 / 유튜브 16:9) (완료·E2E 검증)
메인(촬영 방향) + 반대 방향 버전 자동 생성 — 블러 배경 패딩(split→scale/crop/boxblur→overlay). 상태 API가 altUrl 반환, iOS가 두 버전 모두 다운로드해 앨범 저장("세로·가로 2가지 버전이 앨범에 저장됨"). 멀티포맷 실패 시에도 메인은 정상 완성(부가기능 격리).
완성 후 APNs로 "Vlog 완성됐어요" 푸시 알림 (완료)
워커가 completed 시 sendPush("🎬 Vlog 완성!" + 코스명, type:'vlog_done') 발송. 기존 APNs 인프라 재사용.
iOS 앱 수정
로컬 AVFoundation 합성 → 서버 업로드 방식으로 변경 (완료)
VlogServerService 신규 — 잡 생성→클립 스트리밍 업로드(메모리 미적재, 임시파일 multipart)→start→2초 폴링→완성본 다운로드. VlogGenerationView가 서버 우선, 실패 시(네트워크·서버 다운) 기존 로컬 합성으로 자동 폴백 — 기능 항상 동작 보장. 빌드 통과, 실기기 검증 대기.
처리 중 대기 UI 추가 (진행률 표시) (완료)
기존 진행률 링 재사용 + 단계별 텍스트("클립 업로드 중 (i/n)" → "서버에서 편집 중이에요" → "완성본을 받아오고 있어요"). 서버 progress(0~100)를 링에 실시간 매핑.

⏱ 1~2주 WAS 서버
📡 비유: 전화 vs 편지
지금 Firestore 방식은 "편지를 보내고 상대방이 읽기를 기다리는 것" (3~5초 지연). WebSocket은 "전화처럼 연결이 항상 열려있어서" 위치 변화가 즉각 전달됩니다. 이 연결을 이용해 채팅도 함께 구현할 수 있습니다.
ws 기반 WebSocket 서버 구현 (/ws/location)
WAS에 ws npm 패키지 추가. roomId 기반 브로드캐스트, 30초 heartbeat, 연결 해제 시 자동 정리. Nginx /ws/ 프록시 블록 추가 (Upgrade 헤더).
실시간 위치 공유 Firestore → WebSocket 전환 완료
LocationSocketService.swift 신규 생성. ActiveSessionView에서 Firestore 위치 리스너 제거, WebSocket connect/sendLocation/disconnect로 교체. 지연 3~5초 → 50~200ms.
그룹 실시간 채팅 (단톡·푸시·답장·이모지반응) — 서버 배포 완료
기존 "피드+댓글"(Firestore·비동기)을 방 전체 단톡(WebSocket·실시간)으로 교체. server.js WS에 chat 타입(room_messages 저장 + 방 전체 브로드캐스트 + 메시지별 messageId uuid 부여 + clientMsgId 낙관적 확정), GET /api/rooms/:id/messages 히스토리. iOS ChatSocketService·GroupChatView 신규, RoomDetailView가 단톡 표시(여행 활동은 시스템 메시지로 삽입). ①오프라인 푸시: 접속 안 한 멤버에게 "닉네임: 메시지" APNs(발신자·접속중 제외, 5분 캐시, 무료), 탭 시 방 열림(type:'chat'). ②답장: 꾹 눌러 인용(reply_to 컬럼, 버블 인용블록 + 입력창 프리뷰), 인용블록 탭→원본 스크롤+하이라이트. ③이모지 반응: 꾹 눌러 👍❤️😂😮😢👏 토글(room_message_reactions 테이블, 실시간 브로드캐스트, 버블 하단 반응칩). 2클라이언트 E2E(채팅·푸시·답장·반응토글·히스토리) 전부 통과. iOS 반영은 앱스토어 업데이트 대기.

PM2 클러스터 모드 + pgbouncer
WAS 8코어인데 단일 프로세스면 1코어만 사용 — pm2 -i max로 멀티 프로세스화. DB 커넥션이 프로세스 수만큼 늘어나므로 pgbouncer 커넥션 풀링과 세트로 진행. (주의: WebSocket 방 상태가 프로세스 메모리에 있으면 sticky 세션 또는 Redis pub/sub 필요)
Redis 캐시 도입 (DB 서버에 설치)
인기 코스·장소 캐시·추천 결과 등 반복 조회를 Redis로 → 가장 약한 고리인 PostgreSQL(2코어) 부하 감소. 방화벽 정책 신청서로 WAS→DB 6379 내부 오픈 필요. Phase 8 잔여(TOP10·검색·협업필터링) 고도화와 묶어서 진행하면 효율적.
