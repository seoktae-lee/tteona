1서비스 개요 & 기술 스택

떠나는 "여행을 계획하는 앱"이 아니라 "여행을 기록해주는 앱"이다. 유저가 코스를 만들거나 다른 사람의 코스를 따라 걸으면, 장소에 GPS로 도착하는 순간 앱이 알려주고, 그 자리에서 짧은 클립을 찍으면 하루가 끝날 때 서버가 자동으로 BGM·타이틀·전환효과가 입혀진 Vlog를 만들어준다. 그룹 기능으로 일행과 실시간 위치를 공유하고, 완성된 코스는 탐색 탭과 웹 링크로 다른 여행자에게 퍼진다.

그림 1. 떠나 전체 시스템 구성 — 하이브리드 백엔드 (KISA 3-Tier + Firebase + 외부 API)

처음엔 Firebase 올인원이었다. 그러나 ① Vlog 합성이 폰 CPU를 점유해 발열·배터리 문제를 만들고, ② Google Places 호출이 건당 과금이라 유저 증가 = 비용 폭증 구조였으며, ③ Firestore 리스너 기반 위치 공유는 3~5초 지연이 있었다. KISA 지원사업 선정으로 자체 서버를 확보하면서 "연산은 WAS로, 반복 조회는 PG 캐시로, 실시간은 WebSocket으로" 오프로딩하고, Firebase는 잘하는 것(인증·실시간 동기화)만 남기는 구조로 재편했다.

4인증 & 보안 아키텍처

핵심 설계: "인증은 Firebase가 발급하고, 검증은 모든 곳에서 한다." 자체 서버(WAS)도 세션·JWT를 직접 발급하지 않고 Firebase ID Token을 Admin SDK로 검증한다. 덕분에 iOS·Android·WAS·WebSocket이 단일한 신원 체계를 공유한다.

4-1. 소셜 로그인 4종 통합 (카카오 커스텀 토큰 흐름)

iOS 카카오 SDK로 로그인 → 카카오 액세스 토큰 획득
Cloud Functions createKakaoCustomToken 호출 — 카카오 토큰을 카카오 서버에 검증 후 해당 유저의 Firebase 커스텀 토큰 발급
iOS 커스텀 토큰으로 Firebase Auth 로그인 → 이후 Apple/Google/이메일 유저와 완전히 동일하게 취급
iOS 모든 WAS API 호출 시 Authorization: Bearer <Firebase ID Token> 첨부
WAS requireAuth 미들웨어 — Admin SDK verifyIdToken()으로 검증, 클라이언트가 보낸 userId는 신뢰하지 않고 검증된 req.uid만 사용

Firebase가 공식 지원하지 않는 카카오 로그인을 커스텀 토큰으로 통합했다. 이 선택 덕분에 "카카오 유저용 별도 인증 체계"라는 이중 관리가 사라졌고, WAS는 로그인 제공자를 전혀 신경 쓰지 않는다.

5Vlog 생성 파이프라인 — 이 앱의 심장

유저가 하루 동안 장소마다 찍은 클립들이 서버에서 한 편의 Vlog로 합성된다. v1은 iOS AVFoundation 온디바이스 합성이었고, v2(2026-07)에서 서버사이드 FFmpeg 파이프라인으로 이전했다.

iOS 세션 중 장소 도착 → 지오펜스 감지 → 카메라(AVAssetWriter 커스텀 녹화) → 클립을 Documents/Tteona/Sessions/{sessionId}/에 저장. 동일 장소명 중복 대비 clipFileName으로 파일 고유성 보장
iOS 클립들의 회전 메타데이터(preferredTransform)를 읽어 세로/가로 다수결 판정 → 기본 포맷 결정 (세로=릴스 9:16 / 가로=유튜브 16:9)
WAS POST /api/vlog/jobs — job 생성 (PG vlog_jobs에 소유자·포맷·BGM 기록)
iOS POST /jobs/:id/clips — 클립 순차 업로드 (Nginx가 vlog 경로만 바디 제한 상향)
WAS POST /jobs/:id/start → FFmpeg 합성 시작: 클립 정규화(회전 보정) → 포맷별 독립 합성(릴스/유튜브/1:1 — 블러 패딩 변환) → 타이틀 카드 → 페이드 전환 → 무드별 BGM 믹싱 → 워터마크(무료 유저)
iOS GET /jobs/:id 폴링 — 단계별 진행률 표시 → 완료 시 다운로드 → 사진앱 저장 + 인스타 공유 유도

온디바이스 합성은 iPhone 12 기준 3분짜리 Vlog에 수 분의 발열 구간을 만들었고, 합성 중 앱 이탈 시 실패했다. 서버 이전으로 ① 폰 배터리/발열 해소 ② 멀티포맷 동시 생성 가능(PRO 기능화) ③ 합성 로직 업데이트를 앱 심사 없이 배포. FFmpeg 프로세스는 타임아웃 시 SIGKILL로 강제 회수해 고아 프로세스가 8코어를 잠식하는 것을 방지한다. 이 파이프라인이 유료화(PRO)의 기술적 근거다 — 워터마크 제거·멀티포맷·BGM 선택·장편·우선 처리 모두 서버 파라미터 하나로 게이팅된다.

6실시간 위치 공유 & 그룹 채팅 (WebSocket)

같은 방(그룹) 멤버끼리 세션 중 실시간 위치를 지도에서 보고, 같은 채널로 채팅한다. v1은 Firestore 문서 갱신+리스너(3~5초 지연, 쓰기 과금)였고, v2에서 자체 WebSocket으로 이전했다.

멤버 A (iOS)세션 중 · 위치 스로틀링 송신
멤버 B (iOS)지도에 A 마커 실시간 갱신
멤버 C (Android)동일 프로토콜
↕ wss://…/ws/location — join(토큰+방 멤버십 검증) → location / chat 브로드캐스트
WAS WebSocket 서버roomId → Set<socket> 라우팅
ping/pong 생존 확인 · 금칙어 필터
chat은 PG 저장 후 브로드캐스트 (영속+실시간)
PostgreSQLchat 메시지 영속화 → 재입장 시 GET /api/rooms/:id/messages로 히스토리 복원
그림 3. 방 단위 pub/sub — 인증된 멤버만 조인, 채팅은 저장 후 전파

위치는 휘발성(브로드캐스트만, 저장 안 함), 채팅은 영속성(PG 저장 후 전파)으로 성격을 분리했다. 위치를 저장하지 않는 것은 성능 문제이기 전에 개인정보 최소수집 원칙 — 위치정보법상 이동경로 저장은 민감도가 급격히 올라간다. 클라이언트 중복 수신은 clientMsgId로 제거하고, 백그라운드 전환 시(scenePhase) 송신을 멈춰 배터리를 지킨다.

7푸시 알림 파이프라인 (APNs 직접 + FCM)

앱 기동 시 POST /api/push/register — 디바이스 토큰을 PG device_tokens에 (user_id, platform) 유니크로 upsert
WAS 발송 시점에 유저의 전 플랫폼 토큰 조회 → iOS는 APNs 직접(@parse/node-apn, p8 토큰 인증), Android는 FCM으로 분기
WAS 트리거: ① 코스 좋아요 ② 내 코스 따라가기 시작 ③ 매주 월 09:00 KST 주간 여행 리포트(node-cron, 지난 7일 활동 유저만) ④ 그룹 알림(Cloud Functions — Firestore 문서 생성 트리거)
iOS 수신 → 딥링크 라우팅 (채팅방 열기 / 세션 열기 / 촬영 유도). 활성 채팅 화면에서는 해당 방 알림 억제

iOS 푸시를 FCM 경유가 아닌 APNs 직접 연동으로 전환한 것은 ① 전달 지연 한 홉 제거 ② FCM 콘솔 의존 제거 ③ Live Activity 업데이트 등 APNs 고유 기능의 길을 열기 위함이다. device_tokens를 "유저당 1행"에서 "(유저, 플랫폼)당 1행"으로 무중단 스키마 마이그레이션(기동 시 idempotent ALTER)한 것이 Android 동시 지원의 핵심이었다.

9외부 API 비용 방어 전략 (캐시 계층)

1인 운영 서비스의 생존 조건은 "유저가 늘어도 원가가 안 늘어나는 구조". 떠나는 과금성 외부 API 앞에 전부 캐시를 세웠다.

iOS 장소 사진/상세 필요 → 먼저 GET /api/places/cache?key=…
PG 캐시 히트 → 즉시 반환 (Google 과금 0원). 같은 인기 장소는 전국 유저가 캐시를 공유
iOS 미스 시에만 Google Places 호출 → 결과를 POST /api/places/cache로 적재 — 이후 전 유저 히트
WAS 대중교통 경로도 동일 — Kakao Mobility 결과를 좌표쌍 키로 PG 캐시. TourAPI(무료·공공)를 사진 1순위 소스로, Google을 폴백으로 강등

📉 효과 — 장소 사진·상세 조회의 대부분이 캐시로 흡수되어 Google Places 비용을 사실상 상수로 고정. "유료 API 앞에는 반드시 우리 캐시" + "무료 공공데이터를 1순위 소스로" 두 원칙의 조합.
