## 1. 마스터 스토리 (공통 뼈대)

모든 기업 버전은 이 뼈대의 변주다. 순서 = ①문제 발견 → ②도전적 목표 → ③기술적 깊이 → ④위기와 전환 → ⑤외부 검증 → ⑥회사와의 접점.

> **[갤러리에 묻히는 여행을 구하다 — 기획부터 인프라까지, 1인 풀사이클 2개월]**
>
> 여행에서 수백 장을 찍고도 정리하지 못해 갤러리에 묻어버리는 제 모습에서 출발했습니다. 기록의 병목은 촬영이 아니라 '편집'이고, GPS가 "언제 어디서 찍었는지"를 이미 알고 있다면 편집을 완전 자동화할 수 있다고 가설을 세웠습니다. 그렇게 만든 것이 '떠나' — 코스를 따라 걸으면 지오펜스가 도착을 감지해 촬영을 유도하고, 하루가 끝나면 자동으로 한 편의 Vlog가 완성되는 위치기반 여행 기록 앱입니다.
>
> 처음부터 데모가 아닌 '실제 출시와 운영'을 목표로 잡았습니다. 2개월간 SwiftUI로 iOS 약 21,000줄, Compose로 Android 약 21,000줄, Node.js 서버 3,200줄과 REST 엔드포인트 40여 개를 혼자 설계·구현했고, 소셜 로그인 4종 통합, 한·영·일 3개국어, RevenueCat 구독 수익화까지 상용 서비스 요건을 갖췄습니다.
>
> 가장 큰 전환점은 온디바이스 영상 합성의 한계였습니다. 기기 발열과 배터리 소모가 여행이라는 사용 맥락과 정면충돌한다는 것을 실측으로 확인하고, 합성을 서버로 옮기기로 결단했습니다. 마침 KISA 2026 위치정보 클라우드 지원사업에 사업계획서가 선정되어 3-Tier 인프라(WEB·WAS·DB)를 확보했고, Nginx·PM2·PostgreSQL 위에 FFmpeg 멀티포맷 합성 파이프라인과 WebSocket 실시간 위치 공유·채팅을 직접 구축·운영했습니다. 이 과정에서 아키텍처가 세 번 진화했는데(Firebase 올인원 → 하이브리드), 구버전 앱 사용자를 한 명도 버리지 않는 무중단 마이그레이션을 원칙으로 지켰습니다.
>
> 이 프로젝트가 제게 남긴 것은 세 가지입니다. 첫째, 문제를 계측하고 근본 원인까지 파는 습관 — 14건의 트러블슈팅을 증상→계측→원인→구조적 해결의 형식으로 문서화했습니다. 둘째, 트레이드오프를 언어화하는 힘 — 온디바이스 vs 서버, Firebase vs 자체 DB 같은 선택마다 "무엇을 얻고 무엇을 지불하는가"를 남겼습니다. 셋째, 끝까지 책임지는 오너십 — 기획·디자인·클라이언트·서버·인프라·법적 컴플라이언스(위치정보법, 아동안전정책)까지 전 구간을 완주했습니다.

## 2. 기업별 맞춤 버전

### 2-1. 카카오모빌리티 — "이동의 순간을 데이터로 만든 개발자" ★적합도 최상

카카오모빌리티가 다루는 것이 정확히 이 앱의 심장이다: **이동 중의 위치 데이터, 경로, 지도 위의 실시간성**. 게다가 Kakao Mobility API의 실제 소비자였다는 사실이 강력한 훅.

**인재상 매핑** — 카카오모빌리티는 단일 인재상 문구 대신 "기술로 이동의 문제를 해결"하는 방향성(최근 채용 기조: 피지컬 AI·자율주행 내재화, 플랫폼·백엔드 시스템 설계)을 내세운다. 카카오 공통 문화는 '스스로 문제를 정의하고 끝까지 해결하는 사람'.

| 그들이 찾는 것 | 본문의 증거 문장 |
|---|---|
| 이동 문제의 자기주도적 정의·해결 | "기록의 병목은 편집" 가설 수립 → 지오펜스 도착 감지 설계 |
| 플랫폼·비용 감각 | 경로·장소 공유 캐시로 API 원가를 사용자 수와 디커플링 |
| 위치 데이터의 책임 | WS 도청 취약점 자체 발견·차단, 위치정보법 신고 요건 대응 |

> **[지도 앱은 '가기 전'을, SNS는 '다녀온 후'를 다룹니다 — 저는 '다니는 동안'을 만들었습니다]**
>
> 위치기반 여행 기록 앱 '떠나'를 기획부터 인프라까지 혼자 개발하며, 카카오모빌리티가 매일 다루는 '이동'이라는 도메인에 2개월간 몰입했습니다. 네이버·카카오맵이 "가기 전"을, 인스타그램이 "다녀온 후"를 다룬다면, 떠나는 그 사이 — 이동하는 동안의 경험을 다룹니다. 지오펜스로 장소 도착을 감지해 촬영을 유도하고, 하루의 이동이 자동으로 한 편의 Vlog가 되는 서비스입니다.
>
> 이 과정에서 저는 카카오모빌리티 API의 실사용자이기도 했습니다. 도보 경로 안내에 Kakao Mobility 길찾기 API를 연동하며, 호출량이 사용자 수에 비례해 폭증하는 원가 구조를 발견했고, 서버에 경로·장소 공유 캐시 계층을 설계해 동일 코스를 걷는 N번째 사용자부터는 외부 API 호출이 발생하지 않도록 원가를 사용자 수와 디커플링했습니다. 실시간 위치 공유는 WebSocket 채널로 직접 구현했는데, 초기 설계에서 채널 도청 가능성을 스스로 발견해 idToken 검증과 채널 격리로 보강했습니다. 위치 데이터를 다루는 만큼 위치정보법상 사업 신고 요건까지 조사해 대응했고, 이 설계로 KISA 2026 위치정보 클라우드 지원사업에 선정되어 3-Tier 인프라에서 실서비스를 운영 중입니다.
>
> 제가 확인한 것은 "이동 데이터는 쌓이는 방식이 설계의 전부"라는 점입니다. 떠나에 쌓이는 것은 실제로 걸어서 검증된 코스와 보행 데이터이며, PostGIS 확장까지 로드맵에 담아 두었습니다. 수천만 이동의 실시간성과 데이터를 다루는 카카오모빌리티에서, 위치 도메인의 기술과 법적 책임을 모두 겪어본 개발자로서 '이동의 순간'을 더 나은 경험으로 만드는 데 기여하고 싶습니다.

*(공백 포함 약 1,010자)*

### 2-2. 42dot — "소프트웨어로 이동 경험을 처음부터 끝까지" ★적합도 상

42dot의 언어는 SDV(Software Defined Vehicle)와 풀스택 통합. 훅은 **"이동이라는 도메인 + 센서(GPS) 실시간 데이터 + 클라이언트-서버-인프라를 관통하는 통합 설계"**.

**인재상 매핑** — 42dot Way: ①겸손한 리더십의 팀 플레이어(humble leadership) ②민첩한 실행("완벽보다 빠른 완성, 작게 시작해 빠르게 지속적 결과물") ③투명한 소통(정보·지식 공유) ④지속적 성장(Never stop learning/changing/dreaming).

| 42dot Way | 본문의 증거 문장 |
|---|---|
| 민첩한 실행 | 2개월 만에 데모가 아닌 출시 — 작게 시작해 계속 배포 |
| 투명한 소통 | 트러블슈팅 14건·아키텍처 문서를 공개 형식으로 기록 |
| 지속적 성장 | 아키텍처 3단 진화 — "필요해진 순간에, 근거를 갖고, 무중단으로" |

> **[GPS 한 줄기로 클라이언트·서버·인프라를 관통시킨 경험]**
>
> 42dot이 차량을 소프트웨어로 재정의하듯, 저는 '여행'을 소프트웨어로 재정의하는 실험을 했습니다. 위치기반 여행 기록 앱 '떠나'는 GPS라는 하나의 센서 데이터가 지오펜스 도착 감지 → 촬영 트리거 → 실시간 위치 스트리밍 → 서버 합성 Vlog까지 이어지는, 센서-엣지-클라우드 파이프라인을 1인이 끝까지 설계한 프로젝트입니다.
>
> 이동 중 시스템의 어려움을 몸으로 배웠습니다. 백그라운드에서 위치 스트림을 계속 받으면 배터리가 감당되지 않아 이동 상태에 따른 스로틀링을 설계했고, 일행 간 실시간 위치 공유는 WebSocket으로 직접 구현하며 인증되지 않은 채널 구독 취약점을 발견해 토큰 검증으로 막았습니다. 온디바이스 영상 합성이 발열·배터리 한계에 부딪히자 연산을 서버로 옮기는 아키텍처 전환을 결단했는데, 이때 구버전 앱을 한 명도 버리지 않는 것을 원칙으로 무중단 마이그레이션(단계적 인증 강제, 멱등 스키마 전환)을 수행했습니다. 차량 OTA가 그렇듯, 이미 배포된 클라이언트를 되돌릴 수 없다는 제약 아래에서의 설계였습니다.
>
> 규모는 작지만 전 구간을 관통했습니다. SwiftUI 21,000줄, Compose 21,000줄, Node.js WAS 3,200줄과 REST 40여 개, 그리고 KISA 2026 클라우드 지원사업에 선정되어 확보한 3-Tier 인프라의 운영까지. 완벽한 설계를 기다리는 대신 작게 출시하고 근거가 생길 때마다 구조를 바꿔 온 이 방식이 42dot이 말하는 '완벽보다 빠른 완성'과 닿아 있다고 생각합니다. 도메인 하나를 센서부터 클라우드까지 수직으로 통합해 본 경험으로, 이동의 전 스택을 소프트웨어로 통합하는 42dot에 기여하고 싶습니다.

*(공백 포함 약 880자)*

### 2-3. 삼성전자 (MX) — "온디바이스의 한계를 실측하고, 경계를 다시 그은 경험" ★적합도 상

MX의 핵심 관심사는 **카메라·미디어 경험, 온디바이스 vs 클라우드의 경계, 그리고 양 플랫폼 이해**. 갤럭시의 경쟁 플랫폼(iOS)을 깊게 판 것도 역으로 강점이 된다.

**인재상 매핑** — 삼성전자 인재상 3축: ①열정(Passion, 도전과 책임감) ②창의혁신(Creativity, 틀을 벗어난 문제 해결) ③인간미·도덕성(Integrity). 5대 핵심가치: 인재제일·최고지향·변화선도·정도경영·상생추구.

| 인재상 | 본문의 증거 문장 |
|---|---|
| 열정 | 2개월간 3플랫폼 완주, "데모가 아닌 출시" 목표 |
| 창의혁신 | 발열 실측 → 온디바이스/클라우드 경계를 다시 긋는 하이브리드 재설계 |
| 인간미·도덕성(정도경영) | 위치 데이터 비저장 설계, 아동안전정책, 원본 영상 합성 후 삭제 |

> **[발열 그래프가 알려준 답 — 온디바이스와 클라우드의 경계선 긋기]**
>
> 위치기반 여행 기록 앱 '떠나'를 개발하며, 모바일에서 가장 어려운 두 도메인 — 미디어와 위치를 동시에 다뤘습니다. AVAssetWriter로 커스텀 카메라 녹화를 직접 구현하고, 촬영된 클립을 타이틀·전환·BGM과 함께 한 편의 Vlog로 합성하는 파이프라인을 온디바이스로 먼저 만들었습니다.
>
> 그러나 실측 결과, 합성 중 발열과 배터리 소모가 '여행 중'이라는 사용 맥락과 정면충돌했습니다. 하루 종일 밖에서 쓰는 앱이 저녁에 배터리를 태워버리면 제품이 성립하지 않습니다. 저는 합성을 서버(FFmpeg)로 이전하되, 온디바이스 합성 코드를 폴백으로 유지하는 하이브리드를 선택했습니다. 얻은 것은 발열 해소·멀티포맷 동시 출력·심사 없는 로직 업데이트였고, 지불한 것은 업로드 대역폭과 서버 자원 관리였습니다. 이 트레이드오프를 언어화하는 과정에서, 온디바이스와 클라우드의 경계는 고정된 것이 아니라 사용 맥락이 결정한다는 것을 배웠습니다. 영상 회전 메타데이터(preferredTransform)가 소스마다 달라 합성 결과가 뒤집히던 문제를 회전 정규화 단계로 해결하는 등, 미디어 파이프라인의 디테일도 14건의 트러블슈팅 기록으로 남겼습니다.
>
> iOS(SwiftUI 21,000줄)로 완성한 뒤 Android(Compose 21,000줄)로 주요 기능을 직접 이식하며 두 플랫폼의 카메라·위치·백그라운드 정책 차이를 체득했고, KISA 클라우드 지원사업 선정으로 확보한 인프라에서 실서비스로 운영 중입니다. 매년 수억 대의 기기에서 카메라와 미디어 경험을 책임지는 삼성전자 MX에서, 사용자의 맥락으로부터 기술의 경계선을 긋는 개발자가 되고 싶습니다.

*(공백 포함 약 940자)*

### 2-4. 엔씨소프트(NC) — "라이브 서비스의 실시간성과 미디어 파이프라인" ★적합도 중상

게임사에 여행 앱으로 지원할 때의 훅은 도메인이 아니라 **기술의 동형성**: 실시간 세션(채팅·위치 동기화), 서버 잡 파이프라인, 라이브 서비스 운영 감각.

**인재상 매핑** — NC 핵심가치 3축: ①진지함(Integrity, 일을 대하는 태도) ②열정(Passion, 임무 완수) ③Never-ending Change(끊임없는 발전).

| 핵심가치 | 본문의 증거 문장 |
|---|---|
| 진지함 | 취약점·사고를 숨기지 않고 14건 트러블슈팅으로 문서화 |
| 열정 | 1인으로 클라이언트 2종 + 서버 + 인프라 전 구간 완주 |
| Never-ending Change | 온디바이스 합성 → 서버 파이프라인으로 스스로 뒤엎은 결단, 아키텍처 3단 진화 |

> **[장르는 다르지만, 실시간 세션과 라이브 운영은 같은 문제였습니다]**
>
> 위치기반 여행 기록 앱 '떠나'를 1인 개발하며 마주친 문제들은, 형태를 바꾸면 게임 서버의 문제들이었습니다. 일행과 함께 떠나는 그룹 세션에는 실시간 위치 동기화와 채팅이 필요했고, 저는 이를 WebSocket 채널로 직접 구현했습니다. 초기 설계를 스스로 감사하다가 인증 없이 타인의 위치 채널을 구독할 수 있는 취약점을 발견했고, idToken 검증과 채널 격리를 넣어 막았습니다. 실시간 상태 동기화에서 보안은 기능이 아니라 전제라는 것을 배운 순간이었습니다.
>
> 서버에는 영상 합성 잡 파이프라인이 있습니다. 세션이 끝나면 FFmpeg가 클립들을 릴스·유튜브·1:1 세 포맷으로 동시 합성하는데, 초기에 타임아웃 처리가 없어 고아 프로세스가 서버 자원을 잠식하는 사고를 겪었습니다. 잡 큐(vlog_jobs)와 타임아웃·정리 로직을 갖춘 구조로 재설계하며, 비동기 잡 시스템은 실패 경로가 본체라는 교훈을 얻었습니다. 운영에서도 같은 감각이 필요했습니다. 푸시가 중복 발송되고 자기 행동이 자기에게 알림 오는 문제, 세션 이어하기 시 데이터 무결성이 깨지는 문제를 각각 근본 원인까지 파서 해결했고, 이런 기록을 14건의 트러블슈팅 문서로 남겼습니다.
>
> iOS·Android 클라이언트 각 21,000줄과 서버 3,200줄, KISA 클라우드 지원사업 선정으로 확보한 3-Tier 인프라 운영까지 전 구간을 혼자 완주했습니다. 온디바이스 합성을 스스로 뒤엎고 서버 파이프라인으로 옮긴 결단처럼, 어제의 정답을 버릴 수 있는 태도가 엔씨소프트가 말하는 Never-ending Change라고 믿습니다. 클라이언트와 서버 양쪽의 언어를 모두 쓰는 개발자로서 라이브 서비스의 신뢰성에 기여하고 싶습니다.

*(공백 포함 약 900자)*

### 2-5. KT — "공공 클라우드 사업 선정부터 3-Tier 운영까지" ★적합도 중상

KT의 언어는 **클라우드·네트워크·공공(B2G)·DX**. 훅은 KISA 사업계획서가 '선정'됐다는 외부 검증 + 인프라를 직접 운영했다는 사실. (지원 직무가 클라우드/인프라 계열일 때 최적, 앱 개발 직무면 삼성 버전을 변형해 쓸 것.)

**인재상 매핑** — KT 4대 핵심가치: ①고객(니즈를 치열하게 고민, 새로운 고객경험) ②역량(전문성) ③실질(화려함보다 실질적 성과, 본업인 통신·ICT를 단단히) ④화합(원칙과 소통, 공동체 의식).

| 핵심가치 | 본문의 증거 문장 |
|---|---|
| 고객 | "여행 중 발열로 배터리를 태우면 제품이 성립하지 않는다" — 사용 맥락에서 출발한 판단 |
| 역량·실질 | 계획서로 인프라를 따내고, 장애(nginx 덮어쓰기·NAT IP·APNs 폴백)를 절차 개선으로 남김 |
| 화합 | 배포 후 101 확인을 '절차'로 만든 것 — 재발 방지를 시스템화하는 태도 |

> **[사업계획서로 인프라를 따내고, 그 위에 서비스를 올려 운영했습니다]**
>
> 위치기반 여행 기록 앱 '떠나'를 개발하던 중, 온디바이스 영상 합성의 발열 한계와 Firebase 종량 과금 구조라는 두 벽에 부딪혔습니다. 자체 서버가 필요하다고 판단한 저는 KISA 2026 위치정보 활용 클라우드 지원사업에 서버 활용계획서를 작성해 지원했고, 선정되어 WEB(2C4G)·WAS(8C16G)·DB(2C4G) 3-Tier 인프라를 확보했습니다. 기술이 아니라 계획서로 인프라를 획득한, 제게는 첫 '사업' 경험이었습니다.
>
> 확보한 인프라는 직접 설계하고 운영했습니다. Nginx 리버스 프록시와 PM2 무중단 재기동, PostgreSQL 16 위에 REST 엔드포인트 40여 개와 WebSocket 실시간 채널, FFmpeg 영상 합성 파이프라인, 크론 배치를 올렸습니다. 운영은 문서와 달랐습니다. 배포 스크립트가 nginx 설정을 덮어써 WebSocket 프록시 블록이 사라지고 실시간 채팅이 전면 중단된 사고를 겪은 뒤, 배포 후 WebSocket 핸드셰이크(101 응답) 확인을 배포 절차에 넣었습니다. NAT 환경의 송신 IP가 두 개라는 것을 외부 API 화이트리스트 장애로 알게 됐고, APNs sandbox/production 환경 차이로 인한 푸시 유실은 폴백 로직으로 해결했습니다. 네트워크는 코드가 아니라 경로 전체를 봐야 한다는 것을 몸으로 배웠습니다.
>
> 이 인프라 위에서 iOS·Android 앱(각 21,000줄)이 3개국어로 실서비스 중이며, 구독 수익화까지 갖췄습니다. 공공사업의 요건을 이해하고, 클라우드 인프라를 계획-구축-운영-장애대응까지 완주해 본 경험으로, 대한민국의 디지털 인프라를 책임지는 KT에서 실전형 클라우드 엔지니어로 기여하고 싶습니다.

*(공백 포함 약 920자)*

### 2-6. 두산로보틱스 · HL클레무브 — 지원 시 각도 메모 (솔직한 판단)

이 두 곳은 **도메인 직결성이 약하다** (로봇 제어 / ADAS 인지·제어는 임베디드·C++·제어이론이 중심). 떠나 프로젝트를 메인 소재로 쓰기보다, **보조 소재**로 쓰는 것을 권한다. 그래도 쓴다면 각도는 하나뿐이다:

- **공통 각도**: "실시간 센서(GPS) 스트림을 소비하는 시스템을 끝까지 만들어 봤다" — 위치 스로틀링(전력 제약 하의 샘플링 설계), 지오펜스 이벤트 기반 트리거, 무중단 마이그레이션(배포된 것을 되돌릴 수 없는 제약 = 차량/로봇 OTA와 동형).
- **HL클레무브**: 위치·이동 데이터 처리 경험 + "안전이 전제인 시스템" 서사(WS 인증 강화, 세션 무결성 검증)로 연결. 42dot 버전(2-2)을 ADAS 문맥으로 다듬어 재사용 가능.
- **두산로보틱스**: 연결 고리가 가장 얇다. 떠나는 "끝까지 완주하는 오너십·문제해결 습관"의 증거로만 쓰고, 기술 소재는 다른 경험(로보틱스 유관 과목·프로젝트)을 앞세울 것.
- 두 곳 모두 자소서 문항이 "도전/완수 경험"이라면 마스터 스토리(1번)를 거의 그대로 써도 된다 — 도메인 매칭이 아니라 태도를 묻는 문항이기 때문.
