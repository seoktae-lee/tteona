# 지도 타일 쿼리의 공간 인덱스(GiST) 효과 측정

## 문제
- 떠나 앱은 성수 건물 데이터를 앱 안에 통째로 넣고 있어, 지역을 늘리려면 앱 업데이트가 필요했다.
- 서버가 화면 영역(타일)마다 건물을 골라 주는 API(`GET /tiles/{z}/{x}/{y}.mvt`)로 바꾸면서, "영역과 겹치는 건물 찾기"가 데이터가 늘어도 빠른지 확인해야 했다.

## 가설
- `buildings.geom`에 GiST 인덱스를 걸고 바운딩 박스 겹침(`&&`)으로 거르면, 전체를 훑는 것보다 크게 빨라질 것이다.
- 단, 데이터가 아주 적으면 플래너가 인덱스 대신 전체 스캔을 고를 수 있다.

## 조치
- PostGIS 17-3.5(arm64 네이티브 컨테이너)에 성수 OSM 145동을 멱등 upsert로 적재했다.
- 타일 쿼리: `ST_TileEnvelope`(3857) → 영역을 4326으로 바꿔 `b.geom && 영역`(인덱스 칸을 그대로 비교) → `ST_AsMVTGeom` → `ST_AsMVT`.
- 규모 비교용 합성 데이터: 성수 블록 145동을 40×40 격자로 평행 이동 복제(약 14×21km, 23.2만 동, `source='synthetic'`). 측정 후 삭제했다.
- 같은 타일(z16/55898/25384)에 대해 인덱스 있음/없음을 각각 7회 `EXPLAIN (ANALYZE, BUFFERS)`로 실행하고 Execution Time 중앙값을 비교했다. 인덱스 제거 후 `ANALYZE`로 통계를 갱신했다.

## 측정
- 조건: MacBook(Apple Silicon) 로컬 Docker, PostgreSQL 17 + PostGIS 3.5, 캐시가 데워진 상태(첫 실행 포함 7회 중앙값).

| 데이터 | 인덱스 | 실행 계획 | 중앙값 | 최소~최대 |
|---|---|---|---:|---|
| 실제 145동 | GiST 있음 | Seq Scan | 0.438ms | 0.427~0.550 |
| 실제 145동 | 없음 | Seq Scan | 0.411ms | 0.407~0.462 |
| 합성 23.2만 동 | GiST 있음 | Bitmap Index Scan → Bitmap Heap Scan | **0.829ms** | 0.807~0.855 |
| 합성 23.2만 동 | 없음 | Seq Scan | **14.190ms** | 13.623~14.618 |

- API 왕복(로컬, 실제 145동): 성수 타일 200 OK, 2,533바이트, 18.5ms(curl, 첫 요청 포함).

## 결론
- 23.2만 동 규모에서 GiST 인덱스로 타일 쿼리가 약 17배 빨라졌다(14.19ms → 0.83ms).
- 145동에서는 인덱스가 있어도 플래너가 전체 스캔을 골랐고 시간 차이도 없었다. 행이 적으면 인덱스를 거치는 비용이 더 크다는 플래너의 판단이 맞다.
- 따라서 "인덱스를 걸었다"가 아니라 **실제 규모에서 계획이 바뀌는지**를 확인해야 한다.

## 채택하지 않은 대안
- `ST_Intersects`만 쓰기: 정확하지만 타일 단위 필터에는 바운딩 박스 `&&`면 충분하다. 잘라내기는 `ST_AsMVTGeom`이 한다.
- 영역 대신 geom을 3857로 변환해 비교: 인덱스가 걸린 칸을 함수로 감싸면 인덱스를 못 탄다. 대신 작은 영역 쪽을 4326으로 바꿨다.
- 앱에서 GeoJSON 전체 받기: 지역이 늘수록 다운로드가 커진다. 타일은 보이는 영역만 받는다.

## 남은 한계
- 합성 데이터는 같은 블록의 복제라 실제 도시의 밀도 편차·도형 복잡도와 다르다. 공공 데이터(VWorld) 적재 후 재측정이 필요하다.
- 단일 타일, 단일 연결 측정이다. 동시 요청 부하(k6 p95)와 캐시 적중 효과는 다음 단계.
- 정리 스크립트 첫 버전은 `VACUUM`을 다른 명령과 한 트랜잭션에 묶어 전체가 롤백됐다. 명령을 분리해 수정했다.
