# 타일 결과 캐시: 부하 기준선 대비 효과와 캐시 스탬피드

## 문제
- 캐시 없는 기준선(2026-10-18-5-k6-tile-baseline)에서 한계는 약 6,800rps였고, 병목은 요청마다 같은 타일을 다시 계산하는 DB CPU(약 7.9코어 포화)였다.
- 타일은 데이터를 다시 적재하기 전까지 결과가 같다. 결과 캐시로 DB가 하는 일 자체를 줄여야 했다.

## 가설
- 캐시가 데워지면 DB CPU가 거의 0이 되고 처리량 한계가 크게 오른다.
- 캐시가 빈 상태(콜드)에서 동시 요청이 몰리면 같은 타일을 여러 요청이 동시에 계산할 수 있다(캐시 스탬피드).

## 조치
- Spring Cache + Caffeine, 캐시 이름 `tiles`, 키 `z/x/y`, 최대 2만 장, 쓰기 후 1시간 만료(HTTP max-age와 동일), 통계 기록. 빈 타일도 캐시.
- 무효화: 적재(`OsmBuildingImporter`)가 끝나면 `TileCacheEvictor`가 **트랜잭션 커밋 뒤에** 전체를 비운다(`TransactionSynchronization.afterCommit`). 커밋 전에 비우면 그 틈의 요청이 옛 데이터를 다시 캐시하는 경쟁 조건이 생긴다.
- 테스트 3개: 캐시 적중 시 DB를 비워도 같은 결과 / 재적재 커밋 뒤 캐시 비워짐 / 롤백되면 비우지 않음. "롤백" 테스트는 즉시 비우도록 코드를 망가뜨리면 실패하는 것을 확인했다.
- 측정은 기준선과 같은 스크립트·데이터(합성 23.2만 동, 무작위 z16 타일, 고유 타일 33×46=1,518장)·기기. 적중률은 `/actuator/metrics/cache.gets`의 hit/miss 증가분.
- 콜드 비교: 앱을 매번 새로 띄우고 8,000rps 30초를 `sync=false`와 `sync=true` 각각 3회.

## 측정
- 환경: Apple M4(10코어), k6·앱·DB 같은 기기, PostgreSQL 17 + PostGIS 3.5.

**웜 캐시 (적중률 100%)**

| 목표 rps | 실제 rps | 중앙값 | p95 | p99 | 최대 | 버린 요청 | DB CPU 최대 | 앱 CPU 최대 | k6 CPU 최대 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 100 | 100 | 0.45ms | 0.83ms | 0.99ms | 2ms | 0 | 4% | 1% | 9% |
| 5,000 | 5,000 | 0.05ms | 0.06ms | 0.14ms | 2ms | 0 | 3% | 7% | 44% |
| 8,000 | 8,000 | 0.05ms | 0.06ms | 0.24ms | 4ms | 0 | 4% | 27% | 65% |
| 12,000 | 12,000 | 0.05ms | 0.07ms | 0.31ms | 4ms | 0 | 3% | 48% | 93% |
| 20,000 | 19,998 | 0.05ms | 0.11ms | 0.41ms | 11ms | 51 | 3% | 87% | 150% |

**같은 8,000rps 요청: 기준선 vs 캐시**

| 조건 | 실제 rps | p95 | p99 | DB CPU 최대 |
|---|---:|---:|---:|---:|
| 캐시 없음(기준선) | 6,865 | 344ms | 400ms | 787% |
| 캐시 웜 | 8,000 | 0.06ms | 0.24ms | 4% |

**콜드 시작 8,000rps (앱 재시작 직후, 각 3회)**

| 설정 | DB 계산(miss) | p99 | 최대 | 버린 요청 |
|---|---|---|---|---|
| sync=false (1회 예비 측정 포함 시 1,817) | 1,761 / 1,782 / 1,809 | 6.56 / 16.41 / 34.93ms | 447 / 563 / 602ms | 830 / 837 / 1,498 |
| sync=true | **1,518 / 1,518 / 1,518** | 21.05 / 20.65 / 20.61ms | 546 / 574 / 580ms | 1,207 / 1,243 / 1,154 |

## 결론
- 웜 캐시에서 같은 8,000rps 요청의 p95가 344ms → 0.06ms, DB CPU가 787% → 4%로 줄었다. 20,000rps도 처리했다.
- 20,000rps에서는 k6 자체가 CPU 150%를 써서 **부하 발생기가 먼저 한계**에 가까웠다. 캐시 적용 후 앱의 실제 한계는 이 기기에서 찾지 못했다.
- `sync=true`는 콜드 시 같은 타일의 중복 계산을 없앴다(1,761~1,809회 → 정확히 고유 타일 수 1,518회, 14~16% 감소). 효과는 **DB 보호**다.
- 콜드 p99는 sync=false의 편차(6.6~34.9ms)가 커서 지연 개선이라고 결론 내리지 않는다. sync는 기다리는 요청을 만들기 때문에 지연을 늘릴 수도 있다. 최대 지연 약 550ms는 두 설정 모두에서 앱 기동 직후 JIT 워밍업으로 추정한다.
- 1회 측정만 보고 "p99 41ms → 21ms 개선"이라고 판단했다가 3회 반복 후 철회했다. 반복 측정 없이 결론 내지 않는다.

## 채택하지 않은 대안
- 커넥션 풀 확대: 병목이 DB CPU라 효과 없음(기준선 기록 참고).
- 커밋 전에 캐시 비우기(`@CacheEvict` 기본 동작에 의존): 경쟁 조건으로 옛 타일이 다시 캐시될 수 있다.
- 미리 모든 타일 생성(pre-render): 지역이 늘면 저장량이 커지고 갱신이 무겁다. 요청 시 생성 + 캐시로 시작했다.
- Redis 공유 캐시: 지금은 서버 1대라 앱 메모리 캐시로 충분하다. 서버가 여러 대가 되면 아래 한계를 해결해야 한다.

## 남은 한계
- 앱 메모리 캐시라 **서버가 여러 대면 무효화가 맞지 않는다.** 한 서버에서 적재해도 다른 서버의 캐시는 1시간 동안 옛 타일을 줄 수 있다. 해결 후보: 타일 URL에 데이터 버전 넣기, 또는 Redis Pub/Sub로 무효화 전파(포트폴리오 과제 2와 연결).
- 고유 타일이 1,518장뿐이라 캐시에 전부 들어갔다. 실제 서비스의 다양한 지역·줌에서는 적중률이 낮아지고 최대 크기(2만 장) 조정이 필요하다.
- 콜드 측정 3회는 적다. p99 편차의 원인(JIT, GC, 스케줄링)은 확인하지 않았다.

## 재현
```sh
cd map-api
docker compose up -d --wait
docker compose exec -T postgis psql -U mapapi -d mapapi -f - < scripts/synthetic-grid.sql
./gradlew bootJar && java -jar build/libs/map-api-0.0.1-SNAPSHOT.jar --management.endpoints.web.exposure.include=health,metrics
k6 run -e RATE=8000 load/tiles.js     # 첫 실행 = 콜드, 두 번째부터 = 웜
curl -s 'localhost:8080/actuator/metrics/cache.gets?tag=result:miss'   # 콜드 계산 횟수
```
