# 따라떠나 컨셉 탐색 v2 — "구독"을 떠나답게

> 작성일: 2026-07-13 · 상태: **컨셉 설계 (미개발)**
> 선행 문서: [DESIGN_TTARADDEONA.md](DESIGN_TTARADDEONA.md) (v1 — 기술 뼈대. 데이터모델·규칙·팬아웃은 그대로 유효)

---

## 0. 왜 다시 생각하나

v1 설계는 기술적으로 옳지만 컨셉이 **"인스타 팔로우의 떠나 이식"** 이었다:
버튼 누르면 → 새 글(코스) 알림 → 피드(지도) 우선노출. 어느 앱에 갖다 놔도 성립하는 구조.

떠나에만 있는 자산을 다시 보면, 베낄 필요가 없는 재료가 이미 있다:

| 떠나의 자산 | 인스타에 없는 것 | 코드 근거 |
|---|---|---|
| **발자취 지도** — 정체성이 피드가 아니라 지도다 | 프로필 = 사진 그리드가 아닌 "가본 곳의 지도" | `FootprintMapView`, visitedSigCodes |
| **즉석세션** — "지금 여행 중" 상태가 존재 | 라이브니스. 팔로우엔 '지금'이 없다 | `free_trip_start` 이벤트, `TodaySessionLiveActivity` |
| **코스 = 실행 가능** — 보는 게 아니라 따라 걸을 수 있다 | 콘텐츠가 곧 행동 지시서 | `course_followed`(코스 여행 시작), transit-route API |
| **Vlog 자동 생성** — 여행의 결과물이 영상으로 남는다 | 여정의 '완성품'이 자동 생산됨 | Vlog 파이프라인 |
| **나루** — 배달부 페르소나가 가능한 마스코트 | 알림에 화자(話者)가 있다 | 나루 에셋 7종 |

**핵심 관찰: 여행은 스트림이 아니라 사건(event)이다.**
인스타 팔로우는 "끊임없는 콘텐츠 흐름" 전제라 알림이 피로가 된다. 여행은 드물고, 시작과 끝이 있고, 끝나면 완성품(코스+Vlog)이 남는다. 그렇다면 구독도 **사람의 타임라인이 아니라 "여정"을 구독**하는 모양이어야 한다.

## 1. 컨셉 후보 6가지

### 컨셉 A — 나루 엽서 🕊️ (여정이 끝나면 엽서가 도착한다)
**한 줄**: 길동무가 여행을 마치면, 나루가 그 여행을 엽서 한 장으로 만들어 배달한다.

- **알림이 아니라 우편이다.** "새 코스 업로드" 푸시 대신 — 여행 종료(코스 저장) 시 **엽서**가 생성된다: 앞면 = 코스 대표사진/Vlog 썸네일 + 발자취 스탬프(방문 지역 도장) + 경로 미니맵, 뒷면 = 코스명·장소 목록·"따라떠나기" 버튼.
- 푸시 문구부터 다르다: ~~"OO님이 새 코스를 올렸습니다"~~ → **"🕊️ 나루가 엽서를 물어왔어요 — OO님의 강릉 이야기"**
- 프로필 탭에 **엽서함**: 받은 엽서가 쌓인다. 여행 영감 보관함이자 재방문 루프.
- **왜 떠나만 가능**: 엽서의 재료(경로·지역 스탬프·Vlog 썸네일)가 전부 자동 생성물이다. 작성자가 아무것도 안 해도 엽서가 예쁘다.
- **인프라 접점**: v1의 `onDocumentCreated("courses")` 팬아웃 그대로, payload가 엽서 참조로 바뀔 뿐. 썸네일은 course_thumbnails PG + TourAPI/Google 폴백 재사용.
- **리스크**: 엽서 렌더링(카드 UI) 공수. 서버 이미지 합성은 불필요 — 클라이언트가 데이터로 그리면 된다.

### 컨셉 B — 떠났어요 라이브 🔴 (여행의 '지금'을 구독)
**한 줄**: 길동무가 즉석세션을 시작하면 "지금 OO님이 떠났어요"를 받고, 여정이 실시간으로 진행되는 걸 볼 수 있다.

- 여행 시작: "🔴 OO님이 지금 강릉으로 떠났어요" (지역 단위만 — 정확한 좌표 노출 금지).
- 진행 중: 프로필/엽서함에 "여행 중" 뱃지. (선택) 방문 장소가 하나씩 찍히는 걸 볼 수 있는 관전 모드.
- 여행 종료: 컨셉 A의 엽서로 마무리 → **시작-끝이 하나의 서사**가 된다.
- **왜 떠나만 가능**: `free_trip_start`가 이미 그룹 방에 쏘는 이벤트로 존재. 수신자 집합을 "길동무"로 확장하는 문제일 뿐. Live Activity 인프라도 있음.
- **결정적 전제**: **여행자 쪽 opt-in**. 즉석세션 시작 시 "길동무에게 알릴까요?" 1회 선택(기억됨). 위치 프라이버시는 지역(시군구) 해상도로 제한. LBS 신고 범위 검토 필요.
- **리스크**: 프라이버시 설계가 핵심 난이도. 관전 모드는 Phase로 미루고 시작 알림만으로도 성립.

### 컨셉 C — 발자취 겹쳐보기 🗺️ (구독의 보상이 지도에서 보인다)
**한 줄**: 길동무의 발자취가 내 발자취 지도에 반투명하게 겹쳐진다.

- 내 지도(오렌지) 위에 길동무의 발자취(다른 색 반투명). **"둘 다 가봄 / 나만 가봄 / 그 사람만 가봄"** 3색이 자연히 드러난다.
- "그 사람만 가봄" 지역 탭 → 그 사람이 그 지역에서 만든 코스 목록 → 다음 여행지 영감 엔진.
- 길동무 여러 명이면 "내 길동무들이 가본 곳" 히트맵 모드.
- **왜 떠나만 가능**: 프로필이 지도인 앱이라서. 팔로우의 보상이 피드가 아니라 **내 지도가 넓어져 보이는 경험**이 된다.
- **인프라 접점**: `FootprintMapView`가 이미 sigCode 집합을 그린다. 오버레이는 집합 2~3개를 색만 달리 그리는 문제. 데이터도 `fetchSummary(userId:)` 그대로.
- **리스크**: 기술 리스크 거의 없음. 지도 범례/색 설계만 신경.

### 컨셉 D — 길목 알림 📍 (그 사람의 코스 근처에 갔을 때)
**한 줄**: 길동무의 코스 시작점 근처에 실제로 갔을 때 "여기서 OO님의 코스가 시작돼요 — 따라떠나볼까요?"

- 구독이 "나중에 여기 가면 알려줘"라는 **예약된 여행**이 된다. 알림이 뜨는 순간 = 실행 가능한 순간이라 전환율이 극단적으로 높다.
- 탭 → 코스 상세 → 기존 "코스 따라가기" 여행 시작 → 작성자에게 기존 `course_followed` 알림 → **구독이 실제 여행으로 순환**.
- **왜 떠나만 가능**: 코스가 실행 가능한 앱에서만 성립하는 알림.
- **인프라 접점**: iOS region monitoring(지오펜스, 최대 20개 — 길동무 코스 시작점 상위 N개만 등록) 또는 significant location change + 로컬 판정. 서버 불필요, 로컬 알림으로 가능.
- **리스크**: 위치권한 Always 요구 시 거부감 — "앱 사용 중" 권한 + 지도 열 때 판정하는 보수적 버전으로 시작 가능. 남발 금지(같은 코스 재알림 쿨다운).

### 컨셉 E — 발자취 궁합 🧭 (구독할 이유를 만들어주는 발견 장치)
**한 줄**: 프로필에 "나와 여행 궤적이 74% 겹치는 여행자" — 궁합이 구독 버튼을 누르게 만든다.

- 타인 프로필 헤더에 궁합 배지: visitedSigCodes 교집합/합집합(자카드) 기반. "많이 겹침 = 취향 비슷" + "적게 겹침 = 새로운 세계" 둘 다 후킹 문구로 쓸 수 있다.
- 유저 검색 결과에도 궁합 % 노출 → 검색이 심심한 목록에서 발견 도구로.
- (확장) "나와 궁합 높은 여행자" 추천 섹션 — 구독 유입의 상시 엔진.
- **인프라 접점**: 양쪽 summary는 이미 로드하고 있어 클라이언트 계산으로 충분. 추천 섹션만 서버 필요.
- **리스크**: 지역 수가 적은 신규 유저는 궁합이 무의미 — 최소 방문 지역 수(예: 3개) 미만이면 숨김.

### 컨셉 F — 발자취 이어받기 🔗 (따라간 여행이 관계로 남는다)
**한 줄**: 길동무의 코스를 실제로 따라 여행하면, 내 발자취 지도에 "OO님에게 이어받은 길"로 새겨진다.

- 코스 따라가기로 완주한 여행은 내 발자취에서 그 사람의 색이 섞인 스탬프로 표시. 작성자에게는 "당신의 길을 OO님이 이어갔어요 — 3번째 여행자예요" (마일스톤).
- 코스 상세에 "이 길을 이어간 여행자 N명" — 코스의 사회적 증명이자 작성자 보상.
- **왜 떠나만 가능**: 콘텐츠 소비가 물리적 이동인 앱에서만 "이어받기"가 성립.
- **인프라 접점**: `course_followed`가 이미 있다. 완주 판정 + 발자취 기록에 sourceCourseId 필드 추가.
- **리스크**: "완주" 판정 기준 설계 필요(시작만? 전체 장소 방문?). Phase 후순위.

## 2. 추천안 — 은유를 "팔로우"에서 **"길동무 맺기"** 로

6개는 경쟁 관계가 아니라 **한 은유의 레이어들**이다. 구독을 "그 사람의 여정에 동행자로 이름을 올리는 것"으로 정의하면 전부 자연스럽게 꿰어진다:

```
        [발견]  E. 발자취 궁합 ─── "이 사람, 나랑 겹치네" → 길동무 맺기
          ↓
   [맺은 직후]  C. 발자취 겹쳐보기 ─── 즉시 보상: 내 지도가 넓어진다
          ↓
   [그가 떠남]  B. 떠났어요 라이브 ─── "지금 OO님이 떠났어요" (opt-in)
          ↓
   [여행 끝남]  A. 나루 엽서 ─── 완성된 여정이 엽서로 도착, 엽서함에 쌓임
          ↓
  [내가 근처에]  D. 길목 알림 ─── "여기서 그 코스가 시작돼요" → 따라떠나기
          ↓
   [내가 완주]  F. 이어받기 ─── 작성자에게 보상, 내 지도에 흔적 → 관계 강화 루프
```

**차별점 요약**: 인스타 팔로우는 *콘텐츠 스트림 구독*이고, 길동무는 *여정의 동행자 등록*이다.
알림은 사람이 아니라 **여정의 생애주기(떠남→여행중→엽서)** 를 따라 오고, 보상은 피드가 아니라 **내 지도**에서 보인다.

### 우선순위 판단
| 레이어 | 가치 | 공수 | 판정 |
|---|---|---|---|
| A 나루 엽서 | ★★★ 코어 루프의 감성 차별화 | 중 (카드 UI) | **MVP** — v1의 "새 코스 알림"을 엽서로 승격 |
| C 발자취 겹쳐보기 | ★★★ 맺은 즉시 보상, 공수 대비 최고 | 하 | **MVP** |
| E 궁합 | ★★ 구독 전환 장치 | 하 (클라 계산) | **MVP** (배지만) |
| B 라이브 | ★★★ 가장 떠나다움, 프라이버시 설계 필요 | 중 | Phase 2 (시작 알림만) |
| D 길목 알림 | ★★★ 마법의 순간, 권한 설계 필요 | 중 | Phase 2 (보수적 버전) |
| F 이어받기 | ★★ 장기 리텐션 | 중 (완주 판정) | Phase 3 |

v1의 "지도 우선노출·추천 가산점·필터 칩"은 유지하되 **부가 기능**으로 격하 — 코어 정체성은 엽서와 지도 오버레이가 담당한다.

## 3. 용어 체계 (확정 제안)

| 개념 | 용어 | 비고 |
|---|---|---|
| 관계 맺기(버튼) | **따라떠나** | v1 결정 유지 |
| 맺은 상대 | **길동무** | "팔로잉/팔로워" 완전 대체. 방향 구분이 필요한 화면이 거의 없어 단일 용어로 충분 |
| 여정 완료 배달물 | **나루 엽서** | 알림 아이콘·문구에 나루 고정 등장 |
| 받은 엽서 보관함 | **엽서함** | 프로필 탭 진입 |
| 코스 실행(기존) | 따라가기 | 기존 course_followed 용어 — 변경 없음 |

en/ja: 길동무 = Travel Mate / 旅の相棒, 나루 엽서 = Naru's Postcard / ナルのはがき, 엽서함 = Postcard Box / はがき箱. (확정은 i18n 작업 시)

## 4. v1 기술 설계와의 관계 (무엇이 살고 무엇이 바뀌나)

**그대로 유효 (v1 문서 참조)**:
- `follows/{followerId}_{authorId}` 데이터 모델·Firestore 규칙·복합키 멱등 토글
- `onDocumentCreated("courses")` 팬아웃 함수 골격, 디바운스·차단 필터·FCM 경로 선택
- followerCount 서버 소유 카운터, subNotifEnabled 토글, 알림 라우팅(pendingCourseId)

**컨셉 레이어로 바뀌는 것**:
| v1 | v2 |
|---|---|
| 푸시 "새 코스를 올렸어요" → 코스 상세 | 푸시 "나루가 엽서를 물어왔어요" → **엽서 카드** → 코스 상세 |
| 알림이 끝 (휘발) | 엽서함에 영구 축적 (`users/{uid}/postcards` 서브컬렉션 — 팬아웃 함수가 푸시와 함께 문서 생성) |
| 프로필 CTA만 | + 궁합 배지(E), 발자취 오버레이 진입(C) |
| followerCount 숫자 노출 | "길동무 N명" — 동일 데이터, 용어만 |

**신규 데이터 (Phase별 상세 설계는 착수 시)**:
- `users/{uid}/postcards/{courseId}` — 수신 엽서 (authorId, courseId, courseName, regionStamps[], thumbnailRef, createdAt, read)
- `userPrivate.liveNotifyMates: bool` — 컨셉 B의 여행자 측 opt-in (기본 false)
- 발자취 오버레이는 신규 데이터 없음 (상대 summary 재사용)

## 5. 열린 질문 (개발 착수 전 결정 필요)

1. **엽서 생성 시점**: 코스 저장 즉시 vs Vlog 완성 시(썸네일이 더 예쁨). → 제안: 코스 저장 즉시 생성, Vlog 완성되면 엽서 썸네일 업그레이드.
2. **엽서함 위치**: 프로필 탭 상단 아이콘 vs 탐색 탭 섹션. → 제안: 프로필 탭 (엽서 = 나에게 온 우편이라는 정서).
3. **라이브(B)의 LBS 신고 영향**: 지역 단위 노출이라도 위치기반서비스 신고 범위에 포함되는지 확인 필요 (기존 LBS_FILING.md 검토).
