## 1. Vlog 클립 회전 대참사 — preferredTransform

**상황** — 서버사이드 Vlog 합성(FFmpeg) 전환 직후, 일부 유저 영상에서 세로로 찍은 클립이 90도 눕거나, 가로 클립이 9:16 캔버스에 우표만 하게 박히는 문제.

**원인** — iPhone 카메라는 센서 원본을 그대로 쓰고 **회전 정보를 메타데이터(`preferredTransform`)로만 기록**한다. 온디바이스 AVFoundation은 이를 자동 반영하지만, FFmpeg 파이프라인에서 naturalSize만 보고 합성하면 "픽셀은 가로인데 화면상 세로인" 클립이 뒤집힌다. 클립마다 촬영 방향이 섞이면 단일 캔버스에 정합이 불가능.

**해결**
1. 합성 전 **정규화 단계** 신설 — 각 클립의 transform을 픽셀에 구워(bake) 방향을 통일.
2. iOS에서 클립들의 `naturalSize × preferredTransform`을 계산해 **세로/가로 다수결**로 기본 출력 포맷(릴스 9:16 vs 유튜브 16:9)을 결정, 소수 방향 클립은 블러 패딩으로 수용.
3. 포맷별 합성을 하나의 필터그래프에 욱여넣지 않고 **포맷마다 독립 합성**으로 분리(2026-07-05 개편) — 한 포맷 실패가 전체 실패로 번지지 않게.

**배운 점** — "영상 = 픽셀"이 아니라 "영상 = 픽셀 + 메타데이터"다. 미디어 파이프라인을 옮길 때는 원본 플랫폼이 암묵적으로 해주던 일의 목록부터 만들어야 한다.

## 2. fullScreenCover 전환 타이밍 경쟁 조건

**상황** — 코스 상세(sheet)에서 "떠나기"를 누르면 상세를 닫고 세션 화면(fullScreenCover)을 열어야 한다. 초기 구현은 `dismiss()` 후 `DispatchQueue.asyncAfter(0.5초)`로 세션을 여는 방식 — 기기 성능·애니메이션 상태에 따라 **세션 화면이 안 열리거나 시트가 겹치는** 간헐 버그.

**원인** — SwiftUI는 한 화면에서 modal 전환이 겹치면 뒤의 요청을 조용히 무시한다. asyncAfter는 "닫힘 완료"를 보장하지 않는 추측성 대기일 뿐.

**해결** — **의도를 상태로 승격**시키는 패턴으로 전면 교체:
```swift
.sheet(item: $selectedCourse, onDismiss: {
    if let info = pendingSessionInfo {   // 닫힘이 '완료'된 시점에
        pendingSessionInfo = nil
        courseSessionInfo = info          // 다음 모달을 연다
    }
}) { ... }
```
"떠나기"는 `pendingSessionInfo`만 세팅하고 시트를 닫는다. 실제 세션 오픈은 시스템이 보장하는 `onDismiss` 콜백에서 수행. 방 재선택, 딥링크 진입, 나의오늘 재개 등 **모달 체이닝이 필요한 모든 곳에 동일 패턴 적용** (MainView, MainTabView, ExploreGridView).

**배운 점** — 타이밍에 의존하는 코드는 "가끔" 실패하고, 가끔 실패하는 버그가 가장 비싸다. 프레임워크가 제공하는 완료 시점 콜백에 상태 기계를 얹는 것이 정답.

## 3. git 이력에 남은 시크릿 — 사후 대응과 fail-fast

**상황** — 초기 개발 속도를 위해 서버 코드에 PG 비밀번호·관리자 토큰 등이 리터럴로 존재했던 시기가 있었고, 이 값들은 커밋 이력에 영구히 남는다.

**대응**
1. 소스에서 시크릿 전량 제거 → 환경변수 주입으로 전환.
2. **이력에 노출된 값은 "이미 유출된 것"으로 간주**하고 전부 새 값으로 로테이션.
3. 재발 방지: 필수 환경변수가 없으면 서버가 아예 기동하지 않는 `requiredEnv()` fail-fast 가드 — "환경변수 깜빡하고 기본값으로 조용히 돈다"는 최악의 시나리오 차단.

```js
function requiredEnv(name) {
  const v = process.env[name];
  if (!v) { console.error(`[Config] 필수 환경변수 ${name} 미설정`); process.exit(1); }
  return v;
}
```

**배운 점** — 시크릿 관리의 핵심은 "지우기"가 아니라 "무효화(로테이션)". git에서 지워도 이력·포크·CI 로그에 남는다. 그리고 보안 설정은 "없으면 죽는" 쪽이 "없으면 대충 도는" 쪽보다 항상 안전하다.

## 4. 구버전 앱을 버리지 않는 인증 도입 (AUTH_ENFORCE)

**상황** — 초기 API는 인증 없이 열려 있었고(클라이언트가 userId를 body로 전달), 뒤늦게 전 엔드포인트에 Firebase ID Token 검증을 도입해야 했다. 문제는 **이미 스토어에 토큰을 안 보내는 구버전 앱이 배포돼 있다**는 것 — 서버에 인증을 즉시 강제하면 기존 유저 전원이 하루아침에 API를 잃는다.

**해결** — 2단계 전환 설계:
- `AUTH_ENFORCE=false` **완화 모드**: 토큰이 오면 검증해서 쓰고(무효 토큰은 거부), 안 오면 통과시키되 구버전으로 기록.
- 신버전 앱 보급 후 `AUTH_ENFORCE=true`로 스위치 — 코드 배포 없이 환경변수 하나로 강제 전환.
- 완화 모드에서도 `무효 토큰 ≠ 무토큰`을 구분 — 위조 시도는 완화 모드에서도 401.

**배운 점** — 보안 강화는 기술 문제이기 전에 **마이그레이션 문제**다. "옳은 최종 상태"와 "거기까지 무중단으로 가는 경로"를 분리해서 설계해야 한다.

## 5. 유저당 1토큰의 함정 — Android 지원 스키마 전환

**상황** — `device_tokens` 테이블이 `user_id UNIQUE`(유저당 1행)였다. Android 버전을 출시하자 같은 유저가 iPhone과 갤럭시를 함께 쓰면 **나중에 등록한 기기가 먼저 기기의 토큰을 덮어써** 한쪽 푸시가 끊겼다.

**해결** — `(user_id, platform)` 복합 유니크로 전환. 운영 DB라 다운타임 없이:
```sql
ALTER TABLE device_tokens ADD COLUMN IF NOT EXISTS platform TEXT NOT NULL DEFAULT 'ios';
ALTER TABLE device_tokens DROP CONSTRAINT IF EXISTS device_tokens_user_id_key;
CREATE UNIQUE INDEX IF NOT EXISTS device_tokens_user_platform_idx ON device_tokens (user_id, platform);
```
이 마이그레이션을 서버 **기동 시 자동 실행되는 idempotent 스크립트**로 넣어(`IF NOT EXISTS`, `IF EXISTS`) 몇 번을 재기동해도 안전하게 수렴하도록 했다. 발송부는 "유저의 모든 플랫폼 토큰"을 조회해 APNs/FCM으로 분기.

**배운 점** — 스키마의 유니크 제약은 곧 제품의 가정이다. "유저당 기기 1대"라는 가정은 멀티플랫폼 순간 무너진다. 마이그레이션은 idempotent하게 만들면 배포 순서 걱정이 사라진다.

## 6. FFmpeg 고아 프로세스가 서버를 잠식하다

**상황** — 손상된 클립이나 극단적으로 긴 입력에서 FFmpeg이 끝나지 않고 CPU를 문 채 매달리는 케이스. WAS는 8코어라 몇 개만 쌓여도 전체 Vlog 큐가 마비된다.

**해결** — 모든 FFmpeg 실행을 타임아웃 래퍼로 감쌈:
```js
const p = spawn('ffmpeg', ['-hide_banner', '-y', ...args]);
const to = setTimeout(() => { p.kill('SIGKILL'); reject(new Error('ffmpeg timeout')); }, timeoutMs);
```
- SIGTERM이 아닌 **SIGKILL** — 행 걸린 인코더는 정중한 종료 신호를 무시한다.
- 에러 메시지에 stderr 마지막 800자를 실어 **원격에서 원인 파악 가능**하게.
- job 상태를 PG에 기록해 실패 job이 큐를 막지 않고 유저에게 에러 단계가 전달되게.

**배운 점** — 외부 프로세스를 띄우는 서버는 "그 프로세스가 영원히 안 끝나면?"을 기본 가정으로 삼아야 한다. 리소스 회수는 옵션이 아니라 파이프라인의 일부.

## 7. Google Places 과금 폭탄 예방 — 공유 캐시 계층

**상황** — 장소 사진·상세정보를 Google Places API로 조회하는데 건당 과금. 코스 카드 하나가 장소 3~5곳의 사진을 부르니, 탐색 탭 스크롤 몇 번이 수십 콜 = **유저 수 × 스크롤량에 비례해 원가가 증가하는 구조**.

**해결** — 3중 방어:
1. **PG 공유 캐시** — 장소명 기반 키로 결과를 PostgreSQL에 저장. 인기 장소(성산일출봉, 광안리…)는 전국 유저가 캐시 1건을 공유.
2. **무료 소스 1순위** — 한국관광공사 TourAPI(무료)를 사진 소스 1순위로, Google은 폴백으로 강등. 좌표 기반 선별로 엉뚱한 사진 매칭 방지.
3. 클라이언트 요청에 번들 ID 헤더를 실어 API 키 도용 방어(키 제한과 연동).

**결과** — 반복 조회의 대부분이 캐시에 흡수, Places 비용이 유저 증가와 디커플링됨.

**배운 점** — 종량제 API는 기능이 아니라 **원가 구조**다. "유료 API 앞에는 반드시 우리 캐시, 무료 공공데이터를 1순위로"는 이후 모든 외부 연동의 기본 원칙이 됐다.

## 8. 같은 장소를 두 번 가면 영상이 덮어써진다

**상황** — 클립 파일명을 `순서_장소명.mp4` 규칙으로 생성했는데, "숙소 → 관광 → 숙소"처럼 같은 장소를 다시 방문하는 코스에서 파일명이 충돌해 **앞선 클립이 소리 없이 덮어써짐**. 유저 입장에선 "찍은 영상이 사라졌다".

**해결** — Place 모델에 `clipFileName` 필드 추가, 촬영 시점에 고유 파일명을 확정해 모델에 저장. 경로 해석 로직은 `clipFileName` 우선, 없으면(구버전 세션) 기존 규칙 폴백 — 진행 중이던 세션의 하위호환 유지. 장소명 sanitize(`/`, `:`, 공백)도 함께 정비.

**배운 점** — "자연키(이름+순서)로 파일명을 만든다"는 편한 결정이 중복이라는 현실 데이터를 만나 무너졌다. 식별자는 생성 시점에 확정해서 데이터에 붙여 다녀야 한다.

## 9. 이어하기했더니 찍은 영상이 없다 — 세션 무결성 검증

**상황** — 세션(여행) 상태는 로컬에 저장해 이어하기를 지원한다. 그런데 iOS가 저장공간 부족 시 파일을 정리하거나, 유저가 파일 앱에서 지우면 **"방문 완료(영상 있음)" 상태와 실제 파일 존재가 어긋난다**. 이 상태로 Vlog를 만들면 합성이 깨진다.

**해결** — 세션 복원 시점에 방문 기록 전건에 대해 **클립 파일 존재를 검증**, 파일이 사라진 장소는 방문 상태를 롤백하고 유저에게 무결성 경고를 표시. "다시 찍으면 된다"로 자연 회복되는 흐름.

**배운 점** — 로컬 저장 상태는 "OS가 언제든 파일을 지울 수 있다"는 전제 위에서 설계해야 한다. 상태와 실체가 분리돼 있다면, 복원 시점 검증이 최후의 방어선.

## 10. 푸시가 두 번 오고, 내 행동이 나에게 알림 온다

**상황** — 그룹 알림 초기 구현에서 ① 같은 이벤트에 푸시가 중복 발송되고 ② 내가 좋아요를 누르면 나에게도 알림이 오는 문제 (2026-05-17 수정).

**원인** — ① 알림 트리거가 문서 생성과 delegate 양쪽에 걸려 이중 발화 + iOS 노티피케이션 delegate 메서드 중복 구현. ② 발송 대상 계산에서 행위자 본인 제외 로직 부재.

**해결** — 발송 경로를 단일화(문서 생성 트리거 1곳), 수신자 목록에서 `actorId` 제외를 서버 공통 규칙로. 이후 서버 API에도 동일 원칙(`if (req.uid === courseOwnerId) return skip`)을 일관 적용. 활성 채팅 화면에서는 해당 방 알림을 클라이언트에서 억제해 "보고 있는 대화의 알림이 울리는" 소음도 제거.

**배운 점** — 알림은 기능이 아니라 신뢰다. 중복·자기알림 같은 사소한 결함이 "이 앱 알림은 꺼야지"로 직행하고, 그 순간 리텐션 채널 하나가 영구히 사라진다.

## 11. Vlog 타이틀 카드 렌더링이 너무 느리다 — CALayer 전환

**상황** — Vlog 도입부에 날짜·코스명이 담긴 타이틀 카드를 넣는데, 초기 구현은 타이틀 카드를 **별도 영상 클립으로 렌더링해서 합성** — 몇 초짜리 카드 하나에 인코딩 패스가 통째로 하나 추가되어 합성 시간이 눈에 띄게 늘었다.

**해결** — 타이틀 카드를 영상이 아닌 **`CALayer` 오버레이**(AVVideoCompositionCoreAnimationTool)로 전환 (2026-05-23). 인코딩 패스 1회 절약 + 텍스트가 벡터라 화질 열화도 없음.

**배운 점** — "영상 위에 뭔가를 얹는다"는 요구를 "영상을 하나 더 만든다"로 풀면 비용이 곱해진다. 합성 파이프라인에서는 레이어로 해결 가능한 것을 인코딩으로 풀지 말 것.

## 12. 카카오 로그인을 Firebase에 이식하다

**상황** — 한국 서비스에 카카오 로그인은 사실상 필수인데 Firebase Auth는 카카오를 공식 지원하지 않는다. 별도 인증 체계를 만들면 이후 모든 기능(Firestore 규칙, 서버 인증)이 이중화된다.

**해결** — Cloud Functions `createKakaoCustomToken`: 앱이 받아온 카카오 액세스 토큰을 서버에서 카카오 API로 검증 → 카카오 회원번호 기반 uid로 **Firebase 커스텀 토큰 발급** → 앱은 그 토큰으로 Firebase 로그인. 이후 시스템 전체에서 카카오 유저는 여느 Firebase 유저와 완전히 동일. 계정 삭제 시 카카오 unlink, Apple 자격증명 revoke까지 제공자별 뒷정리를 연쇄 수행.

**함정들** — 카카오 SDK 세션과 Firebase 세션의 수명이 달라 로그아웃/재로그인 흐름에서 상태 불일치가 났고(2026-05-12 안정화), 인증 실패 메시지가 뭉뚱그려져 디버깅이 어려워 에러 원문을 노출하도록 수정(2026-05-07).

**배운 점** — 서드파티 통합의 목표는 "동작하게"가 아니라 **"시스템의 나머지가 그 존재를 모르게"**. 커스텀 토큰 한 층을 만든 덕에 이후 WAS 인증(4번)이 공짜로 통일됐다.

## 13. 실시간 위치 채널의 도청 가능성 — WS 인증 강화

**상황** — WebSocket 위치 공유 초기 버전은 `join {roomId, userId}` 메시지를 신뢰했다. roomId는 추측 가능한 값이라, 악의적 클라이언트가 임의 방에 join하면 **타인의 실시간 위치를 도청**하거나 멤버를 사칭할 수 있는 구조.

**해결** — join 시 ① Firebase ID Token 검증 ② 검증된 uid가 **실제 방 멤버인지 확인** 후에만 입장 허용. 실패 시 명시적 close 코드(4001 인증 실패 / 4003 비멤버)로 종료. 구버전 앱 호환을 위해 REST와 동일한 `AUTH_ENFORCE` 완화 모드를 WS에도 적용. 채팅에는 금칙어 필터를 서버단에서 적용해 차단 시 발신자에게만 통지(에코 차단).

**배운 점** — 위치는 유출 시 물리적 위험으로 직결되는 최고 민감도 데이터다. "누가 이 채널을 엿들을 수 있는가"라는 위협 모델링을 기능 구현과 동시에 해야 하며, REST에만 인증을 걸고 WS를 잊는 것이 흔한 구멍이다.

## 14. 위치정보사업 신고 요건과 TourAPI — 법적 함정

**상황** — 위치기반서비스(LBS)를 운영하려면 「위치정보법」상 **위치기반서비스사업자 신고**가 필요하고, 신고에는 서버 인프라 요건이 있다. 또 관광공사 TourAPI 활용 시 데이터 출처 표기 등 이용조건이 붙는다.

**대응** — KISA 클라우드 선정으로 국내 소재 서버 인프라 요건을 충족 → 사업자 신고 진행 가능 상태 확보. 위치 데이터 설계 자체를 보수적으로: 실시간 위치는 **브로드캐스트만 하고 저장하지 않음**, 세션 위치 추적은 여행 세션 동안만, 개인정보처리방침에 위치정보 항목 명시.

**배운 점** — 위치 서비스는 기능보다 규제가 먼저다. "저장하지 않는 설계"는 성능 최적화가 아니라 컴플라이언스 전략이며, 아키텍처 결정(6장 WS 설계)이 곧 법적 리스크 관리였다.
